# Optional closed-app water notifications

## What is implemented

A browser can opt in to Web Push separately for each device in Water tracker → reminder settings. The message includes the account's first name and may appear on a lock screen. Push subscriptions are account-scoped, and turning off the existing Water reminders toggle stops future scheduler sends for that account. The settings show whether the current device is registered to the signed-in account; this does not confirm that a scheduler is running or that delivery works. The device Disable button removes its server subscription and unsubscribes the browser; Disable on all devices removes all server subscriptions for the account. Up to 10 devices can be registered per account. Pushes continue after sign-out unless disabled; turn them off on shared devices. Removing an account cascades to its push subscriptions. Subscription endpoints and encryption keys are excluded from account export and should not be logged.

The server sends using the existing reminder interval and 08:00–21:00 in the timezone reported by the browser at opt-in. Re-enable on the device after moving time zones or when a VAPID key changes. These are not the unfinished personalized hydration schedules. The existing in-app alarm is separate: its snooze and manual water logs do not reschedule closed-app pushes, and its timer may generate another alert while the app is open. No push Done/Snooze/Skip actions or delivery receipts are implemented. The opt-in message is informational and does not instruct a quantity.

## Server setup (authorized deployment only)

1. Review and back up the authorized database, then apply the additive `migrations/0006_water_web_push.sql` according to the installation's existing migration procedure. It creates one table and a due-time index; it does not change existing water logs. Do not apply it to production without explicit authorization.
2. Use the `web-push` package's CLI (`npx web-push generate-vapid-keys`) in a secure administrator environment. Supply the generated public and private values as `WEB_PUSH_PUBLIC_KEY` and `WEB_PUSH_PRIVATE_KEY`; set `WEB_PUSH_SUBJECT` to an administrator contact such as a valid `mailto:` URI or HTTPS URL. Store the private key securely; the server validates that the public and private keys match. Never commit it or put it in a browser environment variable. Rotating keys requires affected devices to disable and re-enable push.
3. Set `WATER_PUSH_CRON_SECRET` to a cryptographically random secret of at least 32 characters. Store it as a server and scheduler secret, not in source control or logs. The API is unavailable without all four settings. Never expose this secret to a browser.
4. Configure a trustworthy external scheduler under your control to send an HTTPS `POST` to `/api/cron/water-push` once per minute with `Authorization: Bearer <WATER_PUSH_CRON_SECRET>`. No scheduler is run automatically by this repository. As an alternative to cron, run `node scripts/run-water-push-scheduler.cjs` as a supervised long-running process with the same two environment variables; it schedules the next request after the previous one finishes and must remain running. A shell-style command, where both environment values are supplied securely, is:

   `curl -fsS -X POST -H "Authorization: Bearer $WATER_PUSH_CRON_SECRET" "$APP_ORIGIN/api/cron/water-push"`

   Ensure the host is publicly reachable by the scheduler and can reach browser push providers. Manage scheduler retries, secret access and request timeouts securely. Each invocation handles at most 20 due subscriptions in groups of five; larger deployments need sufficient scheduler capacity and monitored backlog. The response reports attempted, provider-accepted, expired and failed counts, not actual device delivery. A claimed event is advanced before delivery to prevent duplicate sends across overlapping invocations; a crash can miss that reminder. Transient transport errors, HTTP 429 and 5xx are retried after about 15 minutes when that is sooner than the normal interval; permanent failures wait until the normal interval. A push service acceptance does not guarantee display.
5. Serve over HTTPS, open the app on each supported device, enable the existing reminder toggle, then choose **Enable on this device** and grant notification permission. On iPhone/iPad, Web Push requires a supported iOS/iPadOS version and a Home Screen web app. Browser, OS, notification settings, battery policies, network access and provider outages can delay or prevent delivery. Opening or installing the app alone does not opt in.

Only approved push-service hosts are accepted to limit server-side request forgery; unsupported providers may not register. A subscription already owned by another account cannot be reassigned or disabled by the current account: sign into the owning account and disable on that device first. After permission is revoked in system settings, remove/re-enable the subscription as needed. In-app reminders remain the fallback. Because pushes may already be accepted by a provider, changing settings cannot retract one in flight.

## Verification and rollback

`node scripts/verify-water-push.cjs` uses synthetic embedded PostgreSQL, mocked auth/origin and push transport and a simulated service worker. It checks migration, allowlist, account isolation, opt-out, quiet hours and DST conversion, overlapping mocked scheduler claims, retries, expired subscriptions, device limits, VAPID key-pair validation, local payload encryption and worker handling. It does **not** verify actual provider delivery, closed-browser or device behavior, real sessions, concurrent PostgreSQL calls, operating system permission prompts, or a running scheduler. Those need a separately authorized HTTPS deployment and real devices.

To stop delivery, stop the scheduler and/or turn off water reminders. Revert the push-specific source and UI only after verifying that other features remain intact. Do not drop the table without an approved backup and retention decision. `web-push` and `@types/web-push` are new dependencies for delivery and types respectively. The installation reported 22 dependency audit findings (19 moderate, 2 high, 1 critical); these are not all attributable to this feature and have not been remediated here.
