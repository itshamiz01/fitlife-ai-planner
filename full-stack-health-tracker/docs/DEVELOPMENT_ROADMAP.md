# Development roadmap — phased, non-destructive

All changes limited to this application unless separately authorized. No deployment, production migrations, paid API use or root app modifications without approval. Existing `docs/audit/PHASE_2_IMPLEMENTATION_PLAN.md` remains useful historical design guidance.

| Priority / phase | Files and work | Dependencies / acceptance / rollback |
|---|---|---|
| 0 audit | This report, FEATURE_STATUS.md, BUGS_AND_ISSUES.md, TEST_REPORT.md and architecture/design documents. | No app changes; preserve prior audit. |
| 1 integrity | Restore missing original, properly licensed `public/icons`, `public/images`, `public/fonts` or use intentionally designed replacements; inspect `public/sw.js`, manifest/layout/CSS. | Asset rights/source needed. Verify every URL, worker installation, offline privacy and mobile layout. Revert asset/config change if regression. |
| 1 baseline | `package.json`, lockfile, lint offenders and scripts after advisory review; `drizzle.config.json` and isolated test configuration. | Disposable PostgreSQL and browser; test lint, typecheck, build, existing suites, audit. Review upgrades separately. No production `push`. |
| 2 preserve records | `src/db/schema.ts`, additive migrations, `src/lib/server.ts`, `api/auth`, `api/profile`, `api/plan`, onboarding UI and tests. | Design provenance, explicit new-user onboarding, user-reviewed demo transfer, immutable plan versions and confirmation; preserve old/unknown records. Isolated migration/rollback and account-isolation tests before production approval. |
| 2 security | `auth-core.ts`, `server.ts`, API routes, infrastructure policy and tests. | Review CSRF/proxy trust, rate/abuse controls, session races, storage encryption and least privilege. Current private API and data remain available. |
| 3 nutrition | `food-catalog.ts`, `planner.ts`, `types.ts`, meal/profile routes, views and new validated calculation tests. | Reviewed sources/units, allergy fail-closed, feasible target and budget outcomes, varied plans, dated logs, source-labelled prices, substitutions; no unsupported clinical claims. |
| 4 training | New structured exercise/session modules, additive schema/routes, `views.tsx` and dialogs. | Actual dated sets/reps/load, limitations/recovery, vetted instructions and progression; distinguish prescription from performance. |
| 5 activity | New owned activity ledger, manual fallback and MET calculation modules; capability/permission UI. | Provenance, timezone, overlap and idempotency first. Native/Health Connect is a separate architecture and consent review; device testing required. |
| 6–7 sleep/body/analytics | Additive storage, owned API routes, UI, export with coverage-aware calculations. | Test overnight/timezone, cross-user access and missing data; secure photo storage separately reviewed. |
| 8 AI | `coach-provider.ts`, `coach-engine.ts`, `api/coach`, `coach-view.tsx`. | User approval before replacing Groq; OpenRouter opt-in with server-side secret, cost control, consent, minimized context, validated outputs, honest failure states and confirmation for writes. |
| 9–11 integration | Dashboard/nav, accessibility, reports, security and mobile tests. | Real datasets, actual device matrix and regression; no fabricated readings. |
| 12 deployment | Document Next runtime/database/backup/secret/rollback compatibility, preserve root workflows. | Approval, production security review, verified restore and deployment authorization. GitHub Pages cannot run Next API routes. |

Every stage: identify changes and side effects before implementation; add regression tests, document actual outcome, keep rollback. Do not claim full product or native tracking completion without the requested evidence.

## Progress after audit

The icon portion of phase 1 has begun: original replacement placeholder icons and a simulated public-shell test were added without changing the service worker or application logic. Browser/device validation and the other missing assets are still outstanding. See TEST_REPORT.md for exact checks and limitations.

A preliminary phase 2 mitigation preserves plan rows for profile saves that do not change planning inputs. Plan-changing saves and refresh remain destructive and need the reviewed archive/versioning design; do not interpret this as completion of phase 2. Changes are isolated to the profile route, a comparison helper, UI copy and a stubbed regression test; revert these code changes to roll back. No migration was added.

A first data-portability step adds a JSON download through an authenticated, origin-checked server route and a Settings control. No import/restore or point-in-time transactional snapshot is provided. Before calling this complete, test against an isolated database with multiple accounts and a real browser; design a validated, conflict-safe import independently. Roll back by removing the export route/component/test and the Settings component reference; no schema or data change is involved.

Plan archive implementation follow-up: `migrations/0001_plan_archives.sql` is additive, and route changes archive snapshots transactionally before replacement. JSON export includes archives where available. Tests use an isolated embedded PGlite database. Production migration requires approval, backup, deployment sequencing and verified restore. In-app restore, retention policy, and concurrent live PostgreSQL testing remain open. Rollback: restore previous route code while keeping the archive table/data; do not drop it. Reverting to old destructive behavior risks data loss and should not be done without another safeguard.

Manual activity follow-up: a separate account-scoped route, nav view, JSON export and additive migration implement initial create/list/delete of manual activity records. Values are explicitly manual, with no invented sensor readings. Editing, aggregation/deduplication, native integration and complete time-zone handling remain open. Rollback: remove the route, UI/nav and export reference while retaining the table and its records; no destructive drop. Review and approve migrations, backups and production rollout separately.

Manual sleep journal follow-up: account-scoped create/list/delete, optional self-rated rest, and JSON export are implemented with an additive migration and embedded-DB tests. No clinical claims or sensor-derived sleep are made. In-app editing, overlap handling, time-zone preference/history and analytics remain open. Rollback removes route/UI/nav/export reference while keeping the table and records; do not drop data. Production rollout requires migration review, backup, testing and authorization.

Plan restore follow-up: `api/plan/archives` and Settings provide owner-scoped archive list and explicit restore, with transactional snapshot of current plan and conservative profile compatibility checks. Tests cover synthetic embedded-DB cases, not actual sessions, concurrency or UI. No additional migration beyond `0001_plan_archives.sql` is required; existing production migration authorization and backup requirements still apply. Rollback removes restore UI/route and restores earlier helper while retaining all archive data; do not drop tables or revert to destructive plan replacement.

Personal journals follow-up: food, exercise and body measurements have shared owner-scoped dated CRUD, validation and JSON export using an additive migration. They are deliberately not merged with planned meals/workouts. They do not provide automatic nutrient totals, exercise progression, photo storage or measurement analytics. Rollback removes UI/API/export access while retaining the table and records; do not drop or truncate them. Live database migration requires separate authorization, backup and test.
